The AI agent security roadmap

Systems that can say no.

AI agents now read email, browse, call APIs, write code, and move money. Most ship with the security model of a demo. This is a maintained, source-checked path from “it works on my laptop” to “we can prove what it did, why, and that it could not have done worse.”

fencing token, n.

A number that goes up every time a lock is granted. The resource rejects any request carrying an older one, so a process whose authority has gone stale cannot act.

#41→reject < 42#42

From Martin Kleppmann, “How to do distributed locking” (2016). The idea behind this project: check authority where the action happens.

The model

The model proposes. The system disposes.

Every serious agent architecture eventually converges on the same idea: the model proposes, the system disposes. The LLM never holds the keys. A deterministic layer decides what is allowed, a sandbox limits the blast radius, and a tamper-evident log records everything.

  1. Break the lethal trifecta. Never let one agent context hold private data, untrusted content, and an exfiltration channel at the same time.
  2. Enforce outside the model. Policies live in code that the model cannot talk its way past.
  3. If it isn't logged, it didn't happen. Every prompt, retrieval, tool call, decision, and approval is recorded so it can be replayed and verified.

01

Prompt injection and goal hijack #

The defining vulnerability of agents. You cannot patch it away; you design around it.

7
  1. ArticlePrompt injection series Simon Willison#

    The running history of the problem, from the person who named it. simonwillison.net

  2. PaperNot what you've signed up for: Indirect Prompt Injection Greshake et al.#

    The paper that showed retrieved content can hijack LLM-integrated apps. arxiv.org

  3. PaperDesign Patterns for Securing LLM Agents against Prompt Injections#

    Six concrete patterns (plan-then-execute, dual LLM, action selector, and more) with trade-offs. arxiv.org

  4. PaperCaMeL: Defeating Prompt Injections by Design Google DeepMind and ETH Zurich#

    Separates control flow from untrusted data and enforces capabilities at tool-call time. Code (research prototype). arxiv.org

  5. ArticleAgents Rule of Two and The Attacker Moves Second#

    Why adaptive attackers break most published defenses, and a simple rule for agent design. simonwillison.net

  6. ArticleEmbrace The Red Johann Rehberger#

    The best ongoing source of real-world agent exploit write-ups. embracethered.com

  7. PaperWhere You Inject Matters: The Trust Region Effect in LLM Agents Guo et al., with Bo Li and Jianfeng GaoNew · 3 Nov#

    With the injected text held fixed, a GPT-5.4 agent followed an unsafe instruction in a README or TODO file 2.6 times more often on average than in a code or data file, so documentation needs at least as much scrutiny as code. arxiv.org

02

Isolation and sandboxing #

Assume the agent will be tricked. Make sure that when it is, it can only break a disposable box.

8
  1. ToolDocker Sandboxes#

    Disposable, isolated environments built for coding agents, each with its own Docker daemon, filesystem, and network, now with microVM isolation. docs.docker.com

  2. ToolgVisor#

    User-space kernel that intercepts syscalls; strong isolation for untrusted agent code without full VMs. gvisor.dev

  3. ToolFirecracker#

    Lightweight microVMs (the tech behind AWS Lambda) for per-task isolation. firecracker-microvm.github.io

  4. ToolKata Containers#

    Containers that run inside lightweight VMs, so you keep the container workflow with VM-grade boundaries. katacontainers.io

  5. CodeE2B#

    Open-source cloud sandboxes purpose-built for running AI-generated code. github.com

  6. CodeNsJail#

    Google's lightweight process isolation using Linux namespaces, cgroups, and seccomp. github.com

  7. ToolWasmtime#

    WebAssembly runtime for capability-based, deny-by-default execution of tools and plugins. wasmtime.dev

  8. CodeSmokescreen#

    Stripe's egress proxy; block agents from reaching internal networks and cloud metadata endpoints. github.com

03

Identity, authorization, and policy enforcement #

The core of "auditable": every action an agent proposes is checked by a deterministic policy, on behalf of a specific identity.

12
  1. ToolOpen Policy Agent (OPA)#

    General-purpose policy engine; write Rego rules that gate agent tool calls. openpolicyagent.org

  2. ToolCedar#

    Fast, analyzable authorization language; policies can be formally verified. cedarpolicy.com

  3. ToolOpenFGA#

    Relationship-based (Zanzibar-style) fine-grained authorization, ideal for "can this agent read this document for this user?" openfga.dev

  4. CodeSpiceDB#

    Open-source Zanzibar-inspired permissions database. github.com

  5. StandardMCP Authorization specification#

    How MCP servers act as OAuth resource servers; required reading if your agents call tools on a user's behalf. modelcontextprotocol.io

  6. StandardOWASP Agent Control Standard (ACS)Added 21 Oct#

    Open standard for runtime hooks and declarative, portable policy enforcement across agent frameworks; the reference implementation (repo) puts a guardian in front of a policy engine. Early (v0.1); its README lists open gaps such as an unauthenticated wire and a fail-open default. genai.owasp.org

  7. PaperLoopjacking: Hijacking Human-in-the-Loop Approval Adithyan Arun KumarAdded 21 Oct#

    Shows how an approval can be decoupled from the action that actually runs, and that exact per-call binding blocks it. arxiv.org

  8. PaperThe Verifiable Action Card Irshad, Mughees, Mughees, Mughees, Soomro#

    Preprint: rebuilds the approval from the pending action and binds approval to the exact action re-verified at dispatch; 0% attack success on the authors' 24-scenario browser-agent benchmark. arxiv.org

  9. PaperAuthority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant Coding Agents Bouras, Dai, MechtaevAdded 29 Oct#

    CapScope derives an authority ceiling from trusted input and checks every tool call against typed capabilities stored outside the model; injected effects ran in 3 of 75 runs, against 33 to 47 of 75 for the baselines. arxiv.org

  10. ArticleMCP Tool Exposure is a Privilege Grant: A Two-Gate Authorization Model Badal Bhushan, CSAAdded 22 Oct#

    Separates which tools an agent may see from whether one specific call on one specific resource may run; tools/list filtering is risk reduction, not authorization. cloudsecurityalliance.org

  11. PaperToolFence Li, He, Dai, XiaoAdded 22 Oct#

    Preprint: compiles a typed authorization blueprint before execution and enforces it with a deterministic monitor that tracks provenance, aimed at attacks that keep the intended tool but manipulate its arguments. arxiv.org

  12. StandardDesign Tenets for Agent Identity Management Systems Booth, Fisher, Galluzzo of NIST and Clancy of MITRENew · 3 Nov#

    Ten initial tenets that will guide the NCCoE's agent demonstrations, including zero standing privilege, separating policy from reasoning ("guardrails alone are insufficient"), deterministic access decisions, and append-only evidence kept independent of the agent. nist.gov

Runtime guardrails #

Guardrails reduce risk; they do not eliminate it. Use them as one layer, never the only layer.

5
  1. CodeNeMo Guardrails NVIDIA#

    Programmable rails for dialog, topics, and tool use. github.com

  2. CodePurpleLlama Meta#

    Includes LlamaFirewall, Prompt Guard, Llama Guard, and CyberSecEval. github.com

  3. CodeGuardrails AI#

    Validators for structured, safe LLM output (validators now ship as PyPI packages). github.com

  4. CodeAgent Governance Toolkit MicrosoftAdded 22 Oct#

  5. PaperBlocking at the Boundary Liu, Han, Lyu, Wang, YuNew · 3 Nov#

    Preprint: confirms staged prompt injections against Claude Code and Codex in their native runtimes, then audits each pending action before it takes effect; its Path-Aligned Attribution auditor reached 86% block recall at a 6 to 8% false-block rate, against 44 to 47% recall for ARGUS. arxiv.org

Audit, observability, and provenance #

The part almost everyone skips. If you cannot replay why an agent did something, you cannot defend it to a customer, an auditor, or a court.

7
  1. StandardOpenTelemetry GenAI semantic conventions#

    The emerging standard for tracing LLM calls, agent spans, and MCP tool calls. github.com

  2. CodeLangfuse#

    Open-source LLM and agent tracing, evals, and prompt management. github.com

  3. CodeArize Phoenix#

    Open-source AI observability and evaluation. github.com

  4. CodeTessera#

    Library for building tile-based transparency logs; a foundation for tamper-evident agent audit trails. github.com

  5. CodeTrillian#

    Google's verifiable log (now in maintenance mode; the design is still worth studying). github.com

  6. PaperAuditable Agents Nian et al., with Yue Zhao#

    Position paper defining five dimensions of agent auditability, from action recoverability to evidence integrity, and proposing an Auditability Card for agent systems. arxiv.org

  7. PaperLLM Agents Can Easily Tamper With Their Own Traces Qin, Schmotz, Prinzhorn, Beurer-Kellner, Prabhu, AndriushchenkoAdded 29 Oct#

    All tested coding-agent harnesses except Muse Code let the agent delete its own traces without tripping monitors; log through an interception point the agent cannot control. arxiv.org

    An eight-phase methodology, from planning to remediation, that covers models, applications, and agents. genai.owasp.org
